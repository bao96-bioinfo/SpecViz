# Contributing to SpecViz

SpecViz is a portable agent skill with Python 3.11+ standard-library helpers.
The maintained package is `skills/specviz/`; installed copies are generated by
`tools/install.py`. Keep framework adapters independent of host integrations.

## Repository layout

| Path | Purpose |
| --- | --- |
| `skills/specviz/` | Skill instructions, runtime helpers, and integration contracts. |
| `tools/` | Installation, packaging, and live host acceptance tools. |
| `tests/` | Automated tests, framework fixtures, and expected text output. |
| `examples/` | Reproducible diagrams and their interpretation models. |
| `docs/` | User guides, compatibility records, and publishing instructions. |
| `.github/workflows/` | Automated checks across Python versions and operating systems. |

## Development

Run from the repository root:

```sh
python3 -m unittest discover -s tests -v
python3 skills/specviz/scripts/specviz_cli.py --help
git diff --check
```

Helpers and tests use only the Python standard library. Tests use temporary
directories for repositories and state. Set `PYTHONDONTWRITEBYTECODE=1` to avoid
creating Python caches while running checks. Name
tests `tests/test_<module>.py` and test observable behavior, source coverage,
scope, evidence provenance, and output meaning. There is no percentage coverage
threshold; supported capability claims need fixtures and recorded acceptance.

If you maintain a local OpenSpec workspace, also run
`openspec validate --all --strict --no-interactive`. The root `openspec/`,
`.agents/`, `.claude/`, and `AGENTS.md` are local authoring files excluded from
distribution; the public test suite does not require them. Nested OpenSpec
examples and fixtures must remain included in Git.

## Style and changes

Use four spaces in Python, descriptive snake_case functions, and explicit
exceptions at input boundaries. Keep imports within the standard library.
Use two spaces in YAML and descriptive Markdown headings. Run the checks above
before opening a pull request; include the problem, behavior, validation, and
related issue or OpenSpec change when applicable. Include before/after text
diagrams when changing visible output. Use concise imperative commit subjects.

## Integrations

See `skills/specviz/references/contracts.md` for source and adapter contracts.
Every supported framework layout needs a versioned fixture with an upstream
source. Native report ingestion and automatic handoffs are separate support
claims. Unit tests do not establish live coding-host acceptance. Record that
acceptance in `docs/acceptance.md` and update `docs/compatibility.md` accurately.

Keep examples as text printed in conversation. Preserve numbers, conditions,
exceptions, source references, and uncertain content when changing layouts.
Generated state belongs outside the project; do not commit installed bundles,
SQLite databases, or distribution artifacts. Existing `AGENTS.md` is preserved.
