# Report comparison and optional code inspection

This miniature reporting service requests password-protected export files. Its
current code deliberately rejects a password. The unchanged export rules and
implementation checklist remain visible alongside the changed design.

The outputs are generated by `tests/test_comparison_examples.py` using the source
files under `project/` and explicit schema-1 handoffs. State is temporary and
outside the example project. The example's test file is inspected as source;
SpecViz does not execute it. Fixed provenance times make the maintained output
repeatable.

| Output | Basis |
| --- | --- |
| `reports.txt` | Earlier completed export design compared with newly requested protection |
| `reports-detailed.txt` | Same hierarchy, including actual implemented text and provenance |
| `code-inspection.txt` | A deliberately overclaiming completion report and contradictory current code |
| `code-inspection-detailed.txt` | Both evidence sources, inspected locations, and unconfirmed test execution |

Raw, portable inputs are also maintained: `report.json` captures the earlier
implementation, `conflicting-report.json` intentionally overclaims the new
behavior, and `inspection.json` records the source-backed contradiction. They
contain relative source paths and retained specification text, so they work in
a copied example project. They are fixture inputs, not generated database state.

The report examples demonstrate a requested change from a valid earlier
implementation. The inspection examples intentionally use another fictional
report that claims the new behavior complete, to show that contradictory
observations preserve both records. None of these synthetic reports establish
real implementation compliance.

Commands in a supported coding agent:

```text
/specviz changes examples/comparison/project
/specviz changes examples/comparison/project --detailed
/specviz changes examples/comparison/project --check-code
```

Use `$specviz` in Codex. For an unfamiliar folder, explicitly select its Markdown
files if automatic discovery finds no specification framework. The helper test
constructs the documented source inventory directly; it does not advertise a
new framework layout.

To reproduce the views from the repository root without a coding agent:

```sh
python3 skills/specviz/scripts/specviz_cli.py changes requirements.md design.md tasks.md --project examples/comparison/project --reports examples/comparison/report.json --detailed --max-lines 200

python3 skills/specviz/scripts/specviz_cli.py changes requirements.md design.md tasks.md --project examples/comparison/project --reports examples/comparison/conflicting-report.json --check-code --inspection examples/comparison/inspection.json --detailed --max-lines 250
```

The helper exposes prose changes as unresolved until an agent supplies the
source-backed semantic correspondence; the maintained report diagrams include
that correspondence. The inspection command consumes the provided fictional
observation rather than inspecting new code or executing tests. For an actual
agent check, request `--check-code` with the copied project's raw report input
and let the agent produce its own observational findings. Helper state stays
in the external user state directory; repeated report delivery is idempotent.
